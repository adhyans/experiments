wifi-live

An ESP32 on the desk listens in 802.11 promiscuous mode and streams every frame header it hears to a browser. Each frame becomes a particle flying inward to the centre, because that is what physically happened: a burst of 2.4 GHz left some device and arrived at the antenna.

The open blocker

The board does not appear on USB

ioreg -p IOUSB -w0 -l lists exactly one device on the bus, a Logitech C920 webcam. No CP2102, no CH340, nothing new. /dev/cu.* shows only Bluetooth-Incoming-Port and debug-console.

That rules out a driver problem. A missing driver still shows the device in ioreg with vendor and product IDs, just without a /dev/cu node. Nothing enumerating means this is electrical.

The board was plugged in with the cable that came with it.

The check that decides it

Look at the small red power LED on the board.

LEDMeaningFix
on Power lines work, data lines do not Charge-only cable. Most likely outcome by a wide margin. Cables bundled with cheap electronics are very often power-only.
off No power reaching the board Cable fully dead, wrong port, or dead board.

Try in this order

  1. A cable you know transfers data. The one used to move files off a phone, not one from a charger box.
  2. Straight into the machine, not through a hub, dock, or monitor. Some hubs cannot supply the ESP32's transmit current peaks and the board browns out mid-enumeration.
  3. The second board. Two were bought precisely for this. If board two enumerates on the same cable, board one is dead and goes back.

Also worth knowing before flashing

The Mac in use is joined to a 5 GHz network on channel 157. The ESP32 radio is 2.4 GHz only, so it physically cannot see that network. Point it at the router's 2.4 GHz band instead, which nearly every router broadcasts alongside the 5 GHz one. Set that channel in CHANNEL before flashing, or set CHANNEL_HOP to true to sweep 1–13 and find what is out there.

Rebuild on a new machine

Two prerequisites: Node (v24 was used here) and arduino-cli. Recreate the tree below, then run these.

1 · Project tree

wifi-live/ firmware/wifi-sniffer/wifi-sniffer.ino # ESP32 sketch, CSV over USB serial bridge/decode.js # 802.11 frame decoding bridge/decode.test.js # contract tests bridge/server.js # serial -> websocket + static host bridge/package.json web/index.html # canvas viewer web/app.js

2 · Bridge

cd wifi-live/bridge npm install node --test decode.test.js # expect 6 pass

3 · Run with no hardware

npm run sim -- --http 7331 # open http://localhost:7331

Synthetic traffic with the same shape as the real thing: beacons at a steady 10 Hz per AP, bursty QoS data from clients, a haze of ACKs. Six fabricated devices.

4 · Toolchain

curl -fsSL https://raw.githubusercontent.com/arduino/arduino-cli/master/install.sh \ | BINDIR="$PWD/.tools" sh export PATH="$PWD/.tools:$PATH" arduino-cli config init arduino-cli config add board_manager.additional_urls \ https://espressif.github.io/arduino-esp32/package_esp32_index.json arduino-cli core update-index arduino-cli core install esp32:esp32

That install is 7.3 GB, most of it the RISC-V compiler and per-variant libraries for chips this project does not use. A WROOM-32 needs only the Xtensa toolchain, esp32-libs, and esptool_py. Trimming to 1.6 GB was verified safe with a clean rebuild giving byte-identical output:

cd ~/Library/Arduino15 rm -rf staging \ packages/esp32/tools/esp-rv32 \ packages/esp32/tools/riscv32-esp-elf-gdb \ packages/esp32/tools/esp32{s2,s3,c3,c5,c6,h2,p4,p4_es}-libs

5 · Flash and go live

# set CHANNEL in the .ino to your router's 2.4GHz channel first arduino-cli compile --fqbn esp32:esp32:esp32 --warnings all firmware/wifi-sniffer arduino-cli board list arduino-cli upload -p /dev/cu.usbserial-XXXX --fqbn esp32:esp32:esp32 firmware/wifi-sniffer cd bridge && npm start -- --http 7331

esp32:esp32 is the generic "ESP32 Dev Module" target and is correct for any ESP32-WROOM-32 board, 30-pin or 38-pin.

What the viewer draws

Centre of the screen is the board. Distance from centre is signal strength. Angle is an FNV-1a hash of the transmitter MAC, so a device always lands in the same place across restarts.

ElementEncodes
cyan particlea data frame
violet particlea management frame (beacons dimmed to 0.3 alpha, they are 10/sec per AP forever)
amber particlea control frame, mostly the ACKs trailing each data burst
particle radius0.9 + log2(len) × 0.34. A 14-byte ACK is ~2.2 px, a 1500-byte frame ~4.4 px
double ringan access point, detected by whether it emits beacons
plain dota client
ringsRSSI at −40, −55, −70, −85 dBm

Radius is signal strength, not distance. They correlate, but walls, bodies, and multipath all push a device outward without it having moved. A dot that suddenly drifts out is usually someone walking between it and the board.

Gotchas already paid for

Each of these cost real debugging time. They are in the code as comments too.

Never call Serial.print in the promiscuous callback

It runs inside the WiFi task. Printing there stalls that task, drops frames, and eventually panics. The callback writes to a lock-free SPSC ring buffer; loop() does the slow I/O.

USB serial, not WiFi, for the uplink

The ESP32 streaming its own output over the channel it is sniffing creates feedback and costs frames. The cable is boring and correct.

Stagger the burst or it fuses into a rail

A burst arrives inside one 50 ms batch. Without a random launch delay every frame in it flies in lockstep and the whole burst renders as one solid line instead of individual frames. Only visible in a screenshot, never in the data.

Report drops, never swallow them

A silent ring-buffer overflow looks exactly like a quiet channel: few particles, no error anywhere. The firmware emits # dropped N every 5 s and the bridge logs it. If it climbs, raise BAUD or RB_SIZE.

HTTP 200 does not mean the WebSocket connected

A 200 proves the page was served, nothing more. The check that means something is the viewer count on the server side. This wasted a cycle: the page served fine while zero browsers were ever connected.

Do not rewrite a status line with \r next to console.log

The carriage-return status line interleaved with console.log and silently ate every connect and disconnect message, making "no viewer ever connected" indistinguishable from "it scrolled past". Now plain timestamped lines every 5 s.

Lima holds ports 8080 and 8090

On the machine this was built on, the Lima docker forwarder claims both. Hence --http 7331 throughout. Check with lsof -nP -iTCP:PORT -sTCP:LISTEN on a new machine.

Open decisions

MAC vendor lookup recommended next

The first three octets of a MAC are an IEEE OUI. An embedded lookup table turns 8E:44:2D into Apple, TP-Link, Amazon. Works fully offline, roughly 20 KB trimmed to common vendors. Held deliberately until real traffic flows: the simulator emits six fabricated MACs, so building it now would be testing against its own fixtures. With 30-odd real transmitters on screen it stops being optional.

Click a device for detail

Side panel with frame-type breakdown, bytes seen, and an RSSI-over-time trace. Turns "that dot is busy" into "that dot moved three metres away 20 seconds ago."

Pause, filters, channel switcher

Nice, but wanted less than expected. The thing is genuinely watchable with no controls.

Options B, C, D from the original plan

OptionWhat it showsExtra hardware
B · CSI waterfall Channel State Information: amplitude and phase across 64 OFDM subcarriers at up to 100 Hz. The multipath structure of the room. Visibly reacts to someone walking past, or to a hand waved near the antenna. The closest thing to watching the field itself. None. Same board.
C · Live spatial heatmap A real spatial field, updating live. Needs many sample points, since one stationary sensor cannot recover space. 6–12 ESP32s reporting over MQTT, interpolated with IDW or RBF.
D · Direction finding True angle of arrival. An actual arrow pointing at the router. KrakenSDR, 5 coherent channels, ~$500.

B is the natural next one: no extra parts, and the firmware already has the flash headroom for it.
